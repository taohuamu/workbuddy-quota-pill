# 设计档案

> 实现细节、设计取舍与验证过程。快速上手见仓库根目录的 [README](../README.md)。

读取本机 WorkBuddy 会话日志中**服务端随响应下发的配额快照**，按模型判断「会不会在配额重置前耗尽」，用于在额度打满之前提前换模型或收尾，而非事后统计已花掉多少。

纯标准库，Python 3.8 以上，只读本地文件，不联网、不登录、不上传。

## 为什么自己写

2026-11 对 GitHub 上 WorkBuddy 生态做过一轮调研。同类工具以 token 与积分的事后统计为主，未发现读取模型级配额百分比的实现。

原因不难理解：配额百分比不存在于任何独立文件中，只随每轮请求写进会话日志。按 token 字段扫描的实现通常不会读到 `providerData.rawUsage.quota`，这条路就被跳过了。

## 数据来源

```
%USERPROFILE%\.workbuddy\projects\<project-key>\<session-id>.jsonl
```

国际版为 `~/.workbuddy-ai/projects/...`，可用环境变量 `WORKBUDDY_HOME` 覆盖根目录。

关键记录形如：

```json
{
  "type": "function_call",
  "timestamp": 1793898134014,
  "providerData": {
    "model": "deepseek-v4.1-flash",
    "rawUsage": {
      "prompt_tokens": 32735,
      "completion_tokens": 196,
      "total_tokens": 32931,
      "credit": 0.11,
      "quota": {
        "model": "deepseek-v4.1-flash",
        "percent": 2,
        "reset_at": "1793975887",
        "shared_models": []
      }
    }
  }
}
```

| 字段 | 含义 | 备注 |
|---|---|---|
| `quota.percent` | 该模型配额已用百分比 | 整数，精度限制见下文 |
| `quota.reset_at` | 配额重置时间戳 | 秒级；本机为 24 小时窗口，每天 22:38 重置 |
| `quota.shared_models` | 共用同一配额的模型 | 非空时消耗互相影响 |
| `rawUsage.credit` | 本次请求消耗积分 | 用于累计，不参与判定 |
| `rawUsage.total_tokens` | 本次请求 token 数 | 同上 |

`percent` 与 `reset_at` 随响应下发，不发起对话就不刷新，因此报告中的时间即「最后一次响应」的时间。

## 哪些模型有配额

以 `providerData.model` 为键，按「该条记录是否包含 `quota` 字典」统计。早期用 `'"quota"' in line` 预筛会把分母缩小，得出「几乎全都有」的错误结论，该口径已废弃。

| 模型 | 记录数 | 带 quota | 情况 |
|---|---:|---:|---|
| `deepseek-v4.1-flash` | 3318 | 491（15%） | 唯一有百分比的模型，且只出现在 11-06 01:02 之后的会话中 |
| `deepseek-v4-pro` | 424 | 0 | 全部发生在 10-28 ~ 10-29，当时字段尚未下发 |
| `glm-5.3-flash` | 187 | 0 | 10-27 ~ 11-06 02:14 全部缺失，11-06 起为 `null` |
| `hy4-free` | 180 | 0 | 免费模型，`credit` 恒为 0，走限流而非配额 |
| `hy3` | 33 | 0 | 同上 |

需要两个维度叠加才解释得通：

- **时间维度**：`quota` 字段从 11-06 01:02 起才随响应下发。此前的 45 个会话（含 deepseek 的 867 / 671 / 430 条）一条都没有，所以「旧日志里查不到上限」不是工具漏读，而是当时服务端未下发。
- **模型维度**：同一时间窗内（11-06 01:02 之后），deepseek 全部带 quota，GLM 全部不带。同版本、同会话、同并发，唯一变量是模型，可判定 GLM 不在 24 小时模型配额这套机制内。

看不见上限的场景与原因：

| 场景 | 现象 | 原因 |
|---|---|---|
| GLM 系列 | 永远无百分比 | 按积分倍率计费（`credits: x0.08`），服务端不下发 quota |
| `hy3` / `hy4-free` | 无百分比、无积分 | 走 `ModelRateLimitCap` 限流，可切付费版（`hy4free` → `hy4std`） |
| 11-06 之前的记录 | 无百分比 | 字段尚未开始下发 |
| 新装或未用过的模型 | 列表里不出现 | 只有用过才有记录 |
| 长时间不对话 | 数字停住 | 快照随响应下发，不请求不刷新 |
| 账号级额度包余额 | 完全不可见 | 需登录态查 Billing 接口，本机凭据为 `$wbEncrypted`，本项目不涉及 |

概括：这套 24 小时配额只覆盖 deepseek 一类模型；GLM 的「额度」是积分，而积分余额在本地没有落点。

## 数据层

### 命令行

```bash
python quota_watch.py                 # 表格报告
python quota_watch.py --json          # 机器可读
python quota_watch.py --window 120    # 用最近 120 分钟算增速（默认 60）
python quota_watch.py --warn 6        # 预计 6 小时内触限则告警（默认 3）
python quota_watch.py --warn-only     # 无风险时静默，适合定时任务
```

退出码：`0` 无风险，`1` 存在 `critical`。配合 `--warn-only` 可让计划任务只在真正出问题时通知。

Windows 下可双击 `run.bat`，等价于 `python quota_watch.py`，结束前暂停以便查看结果。

### 处理流程

**一、采集。** 全量扫描 `projects/*/*.jsonl`，先做 `'"quota"' in line` 字符串预筛，命中才 `json.loads`。48 个文件、45 条快照约 0.2 秒。

**二、增速。** 以最新快照为锚点，取 `--window` 内首尾两条，`rate = Δ百分比 ÷ Δ小时`。窗口内不足两条时，退化为「所有低于最新值的记录 + 最新一条」；仍不足则取最后两条。

**三、置信度。** `percent` 为整数，短样本会放大速率，因此分档：

| 档位 | 条件 |
|---|---|
| high | 跨度 ≥ 120 分钟且涨幅 ≥ 3% |
| medium | 跨度 ≥ 30 分钟且涨幅 ≥ 1% |
| low | 其余，含数据不足 |

**四、周期口径**（`PERIOD_H = 24`）。配额池按 24 小时轮回。`reset_at` 是**下一次**重置时刻，故本周期起点为 `reset_at - 24h`。两处按此边界处理：

- **过期快照**：若 `now > reset_at`（含 60 秒宽限），该快照属于上一周期，模型在本周期尚未使用。它被标为 `stale`，不显示、不参与判定。否则会出现「重置后一次没用，却显示 11%、距重置已过期」的自相矛盾读数。
- **tokens 与积分**：只累加本周期内的快照（`tokens_cycle` / `credit_cycle`），与界面上的百分比属于同一段账。历史累计保留在 `tokens_total` / `credit_total`。

**五、判定**，按顺序执行，命中即返回：

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 已用 ≥ 95% | `critical` 已到上限 |
| 2 | 置信度低且已用 ≥ 80% | `critical` 按最坏打算 |
| 3 | 置信度低，其余情况 | `idle` 只报现状，不预测 |
| 4 | 预计触限早于重置时间 | `critical` 重置前会耗尽 |
| 5 | 预计触限 < `--warn` 小时 | `warn` |
| 6 | 其余 | `ok` |

## 展示层

右下角一块无边框卡片，把上表压成「模型 / 百分比 / 一句判决」。数字全部来自 `build_report()`，展示层不重算、不改写任何判定。

| 形态 | 尺寸（逻辑像素） | 内容 |
|---|---|---|
| 胶囊（默认闲置态） | 150 × 32 | 状态灯 + 最近使用的模型 + 百分比 |
| 卡片（悬停展开） | 250 × 110 起，随空档自适应，上限 306 | 模型 / 进度条 / 判决 / 重置时间 |
| 完整报告（独立窗口） | 罩住对话内容区：宽 870，底边停在输入框上沿之上 | 每个模型的增速、触限预测、样本、tokens、积分 |

```
┌───────────────────────────────┐
│ ● 配额胶囊           02:40  × │
├───────────────────────────────┤
│ deepseek-v4.1-flash      55%  │
│ ▬▬▬▬▬▬▬▬▬─────────────────────  │
│ 重置前耗尽 · 约 1.1 小时后     │
├───────────────────────────────┤
│ 重置 22:38 · 587 条快照  共 1 个│
└───────────────────────────────┘
```

启动即为胶囊，不先展开一次。鼠标停留 180ms 展开，移开 2.2 秒收回。

展开是原地生长：**右下角固定不动**，底边不移、向上向左长，与胶囊连成一体。不压输入框依靠横向躲进输入框右侧空档，详见下文「摆放逻辑」。

### 出现与退出

跟随 WorkBuddy 的**可见主窗口**，而非仅跟随进程：

| WorkBuddy 状态 | 小窗 |
|---|---|
| 打开且在前台 | 出现 |
| 切到其它应用 | 约 3 秒后让路，切回立即出现 |
| 关闭主窗口 / 退到托盘 / 最小化 | 约 1.5 秒后隐藏 |
| 从托盘重新打开 | 重新出现 |
| 进程退出 | 约 10 秒后自身退出 |

三项判据都需要的理由：

- **只盯进程**：关闭主窗口后小窗仍在（WorkBuddy 支持关闭到托盘）。
- **只盯窗口**：WorkBuddy 进程内常驻 `MSCTFIME UI`、`HintWnd`、`Sogou_TSF_UI` 这类 0×0 输入法辅助窗口，它们 `IsWindowVisible=True` 且有标题，会被误判为主窗口。于是主窗口关闭后状态仍为 open，小窗永不隐藏，还会置顶浮在其它应用之上。现行判据要求：真实尺寸（≥ 200 × 150）、无 owner、非工具窗口、非最小化、未被 DWM 隐藏（cloaked）。
- **不看前台**：在其它应用中输入时，置顶胶囊仍压在上面。现行规则是前台为其它应用超过 3 秒即让路，点击小窗本身不触发（自身进程被排除）。不需要该行为时，右键取消「切到其他应用时隐藏」。

表中秒数为 `Lifecycle` 的判定阈值，不等于实际反应时间。落地要叠三段：探测线程最多 1.5 秒才看到状态变化，UI 心跳最多再晚 1.5 秒记录时间戳，之后才是阈值本身。因此「1.5 秒」档实测落在 1.5 ~ 4.5 秒，典型约 3 秒；「3 秒」档落在 3 ~ 6 秒。

冷启动（如登录自启）后若 5 分钟内未见 WorkBuddy，程序自行退出，不留孤儿进程；`--grace 0` 改为一直等待。

两种收尾方式，区别仅在 WorkBuddy 真正退出之后：

| 模式 | 行为 | 适用 |
|---|---|---|
| 默认（跟随） | 应用退出后，小窗 10 秒后结束进程 | 自启由看门狗负责，小窗不常驻 |
| `--resident` | 应用退出后只隐藏，进程留着等待再开 | 要求随时点开即出现，且不在意一个 90MB 进程 |

`--install` 装入的是**看门狗 + 跟随模式**：登录时只启动一个约 27MB 的 WSH 脚本（由 `tools/watchdog.tpl` 生成），每 5 秒检查 `WorkBuddy.exe` 是否存在，存在则拉起小窗；WorkBuddy 退出后，小窗按跟随模式自行结束。因此登录后不存在常驻的 python 进程。

手动点 × 关闭小窗会写入 `suppress` 标记，看门狗在 15 分钟内不再拉起（否则关闭后 5 秒又会出现）。期间如需使用，双击 `tray.bat`。

### 启动参数

```bash
python quota_tray.py              # 本次常驻
python quota_tray.py --install    # 写入登录启动项：开机静默待命，WorkBuddy 一开即出现
python quota_tray.py --uninstall  # 移除
python quota_tray.py --always     # 不看 WorkBuddy，强制显示（预览与截图用）
```

双击 `tray.bat` 等效，它会自动选择一个包含 tkinter 的解释器，控制台窗口随即消失。

小窗用标准库 tkinter 绘制，不引入第三方包。若当前 `python` 未编入 tk，`--which` 会列出本机所有解释器及各自的 tk 状态；`tray.bat` 与 `--install` 会自动选择带 tk 的解释器（优先 pythonw，避免弹出控制台）。本机实测：`.workbuddy/binaries/python` 下的三个解释器均无 tkinter，系统安装的 Python 3.14 有。

### 交互

| 操作 | 效果 |
|---|---|
| 拖动 | 横向纵向均可，胶囊态也可拖；拖动只改本次会话的位置，不写盘，需右键「保存当前布局」才固化 |
| 悬停 | 停留 180ms 展开，快速划过不触发 |
| 单击胶囊 | 立即展开 |
| 移开 | 2.2 秒后收回；鼠标仍在卡片上则续期，拖动中或锁定时不收回 |
| 单击某行 / 「详情」 | 打开完整报告窗口 |
| 右键 | 刷新 / 完整报告 / 在控制台打开 / 复制摘要 / 保存当前布局 / 恢复默认位置 / 重新校准位置 / 切到其他应用时隐藏 / 保持展开 / 置顶 / 开机自启 / 重启小窗 / 退出 |
| × | 退出 |

窄卡（column 模式）放不下「详情」按钮时将其隐藏，右键菜单中仍有「完整报告」。

报告窗标题栏按钮（⟳ / ×）有悬停圆底反馈；小窗「详情」是常驻细边框的圆角按钮。报告窗整窗可拖，内容区按住亦可拖动（画布上没有可点选元素，不会抢滚动），右键菜单同样可保存或复位位置。

默认落点为距工作区右边 8、下边 35（Tk 单位，150% 缩放下即物理 12 / 52），落在任务栏上方的输入法悬浮栏之上。

布局存于 `%LOCALAPPDATA%\quota-watch\tray.json` 的 `layout` 子树，`tray` 与 `report` 两段，均为「距工作区右下角的偏移」：

```json
{"layout": {"tray": {"dx": 24, "dy": 51}, "report": {"dx": 261, "dy": 493}, "saved_at": "11-07 01:20"}}
```

存偏移而非绝对坐标，换分辨率或缩放后「贴着右下角再挪一点」的意图不会漂移。旧版本只有平铺的 `dx/dy` 与 `report_dx/report_dy`，读取时仍兼容；保存后只把**本次写入的那一段**迁入 `layout` 并清除其旧键，另一段的旧键必须保留，否则保存小窗会连带清掉报告窗位置。

小窗偏移存的是右下角锚点，窗口变宽时向左生长，右缘不动。因此收起为胶囊、展开为卡片，两者右下角完全重合。

### 摆放逻辑

前提事实：WorkBuddy 的输入框是一块有限宽的圆角卡片（本机实测 `x 832~2148, y 1278~1477`），并非通栏底边；其右侧到屏幕右缘还留有约 400px 空档。因此「不遮挡」的正解是**横向**避让，而非纵向抬升。早期版本按「底部整条都是输入区」估算，无论怎样调整都会压住。

`_plan()` 一次算出「卡片宽度、行数、底边位置」，按优先级分三档：

| 模式 | 触发条件 | 行为 |
|---|---|---|
| `gutter` | 量到输入框右边缘，且右侧空档 ≥ 196 | 宽度收进空档（本机 376），底边不动，向上生长 |
| `column` | 量不到边缘，或空档不足 | 宽度沿用胶囊那一列（已证明不压输入框），只增高度 |
| `free` | 取消右键「展开时不压输入框」 | 自由浮动，宽度 306，可能压住 |

边缘测量方式：在胶囊中线附近取**三条**横线（`grab_strip`，各约 1~3ms），逐列统计「与背景色显著不同」出现在几行中，从右往左找第一条在多行上重复出现的竖线，即输入框右边框。

判据是「竖线」，不依赖主题明暗。早期版本要求「边框左侧是实心块」，而浅色主题下输入框为白底白字加一条细灰边，该条件恒不成立，校准无法取得数值（issue #1）。阈值取 14：浅色主题下白卡（255）与页面底色（251）仅差 12，门槛再放宽就会把卡片内部特征当成边框。

扫描带右端停在**胶囊左缘减去自身阴影**（`origin[0] + win_w - 2*shadow - pill_w - shadow - 6px`）。窗口为分层透明窗，胶囊左侧大片区域虽属窗口，但绘制为全透明，截屏得到的是宿主界面本身，可正常采样——这也是「输入框右缘落在窗口范围内」仍能测到的原因。反之，一旦采到胶囊自身的投影，那条渐变竖边会被当作边框，卡片越校准越窄。

不能按**窗口左缘**截断：窗口恒为展开尺寸，比胶囊宽得多，左缘常已落在输入框右缘左侧（issue #1 复测时 `origin[0]=2061`，真实边框在 2149），从此处截断永远够不到边框，只能测到左侧无关竖线，卡片反而压到输入框上。

测得后写入 `tray.json` 的 `input_edge`，之后复用；息屏、全黑或被其它窗口遮挡时读不到，退回 `column` 模式。读屏节流 5 秒，展开态一律只读缓存——展开的卡片正压在扫描线上，现场测量的结果是卡片自身左缘。

校准（右键「重新校准位置」）会先把窗口收成胶囊再读屏，量完自检一次：按新边界算出的卡片左缘必须落在边界右侧，否则不采用。

右缘另有一条独立规则：`_place()` 一律让窗口右缘距屏幕右缘至少 16 逻辑像素（`RIGHT_RESERVE`），为宿主窗口贴边的滚动条留出位置。

底边默认落点为 `BOTTOM_PIN = 34` 逻辑像素（输入框底边距工作区底部，本机实测 1477/1528），因此初次安装时胶囊、展开卡片与输入框底边平齐。该值只用于默认落点与「恢复默认位置」，不再每帧强制钉底，小窗可自由拖到任意高度。

### 视觉

几个刻意取舍：

- **三级灰阶**：模型名（正文色）> 判决语（次级灰）> 页脚（再淡 30%）。视线先落在模型与百分比，需要解释时才往下读，元信息放在最后。
- **行间发丝线**：行高 56 后，名称、进度、判决三段各有呼吸空间，行间再压一条极淡分隔线，判决语不会与下一行的模型名黏连。
- **百分比等宽**：Cascadia Mono → Consolas，字号比模型名大一号、右对齐，数字从 9% 跳到 10% 时不会左右抖动。
- **进度条 5px 高**，两端圆角，填充上压一道 26% 白色高光。Tk 无 alpha，该高光由混色算出。
- **阴影三层**，由外到内递深，替代真实模糊阴影；卡片圆角 13。
- **颜色只表达判定**：红 / 橙 / 绿 / 灰对应 `critical` / `warn` / `ok` / `idle`，不做装饰性上色。
- **空态与错误态是一枚小表盘**：`create_arc` 画 220° 圆弧加指针，配居中两行说明；卡片过矮（窄卡）时退化为纯文字居中。
- **胶囊灯取全场最危险档位**（`worst_level`），而非最近对话模型的档位。本工具的职责是指出哪个模型先撞墙，因此收起态只要有模型接近上限就应亮红。胶囊文字仍显示最近对话的模型及其自身百分比，数字颜色随自身档位（0% 为灰）。灯与数字各表一处。
- **深浅色跟随系统**：每 30 秒读一次注册表 `AppsUseLightTheme`，切换主题无需重启。
- **按像素省略**：模型名按字体实测宽度二分截断，长名称可多显示两三个字。
- **收起与展开固定右下角**：形态切换按右下角锚点重算，配合 130ms 缓出动画。
- **完整报告是真正的窗口**：宽 870 逻辑像素，约等于输入框横向跨度；右缘与输入框右缘平齐（量不到时水平居中）；顶部距工作区顶 48 逻辑像素；底边让开输入框上沿右侧的吉祥物（`INPUT_GAP = 162`）。拖动后标题栏右侧浮出「保存位置」按钮，点击才固化。存档与小窗共用 `layout` 子树，取 `report` 段。
- **标题栏与卡片同色并附底部分隔线**，整窗融入 WorkBuddy 的白色系（深色主题同理）。
- **内容列限宽居中**（最大 700 逻辑像素），卡片 → 图例（一行四档色标）→ 页脚建议排成内容栈：放得下整体垂直居中，放不下则整栈滚动，标题栏固定，右缘有细滚动指示条。早期版本卡片按绝对坐标绘制，模型较多时漫过图例区，已修正。
- **每张模型卡为白卡 + 细边 + 浅影 + 左侧档位色条**：名称与百分比 → 进度条 → 判决语；分隔线以下两行「标签 + 值」（重置 / 增速 / 距重置，触限预测 / 样本 / 置信），末行为 tokens 与积分。底部建议置于语义色淡底提示框，有风险时为红调，否则为灰底。

### 开销

全量扫描日志为数百毫秒量级（本机 58 个会话文件 / 76MB / 1348 条快照，实测 660ms），随日志增长而增加，故放在后台线程；报告窗的 ⟳ 刷新同样后台读取，标题栏不冻结。

进程与窗口探测常态约 4ms（窗口枚举 2ms，校验缓存 pid 1.3ms）。10ms 量级的进程全量枚举（300 以上进程）只在缓存失效或每 20 秒兜底重扫时发生，因为 WorkBuddy 的 pid 在会话内几乎不变，常态只需 `OpenProcess` 加核对 exe 名（约 0.05ms/个）。

探测在后台线程，1.5 秒一次（`--poll`），对应单核约 0.25% CPU。隐藏阈值只有 1.5 秒，探测周期必须跟上，因此隐藏态不降频。只有 `--resident`（应用退出后长期待命）在 gone 状态用 5 秒周期（`--poll-idle`）。

## 设计取舍

- **不比绝对值，只比重置时间。** 剩 50% 但一小时消耗 30% 才危险；剩 20% 但还有 20 小时才重置则安全。百分比本身没有决策意义。
- **用滑动窗口而非累计均值。** 累计会把上周的重度使用带入，导致休息时仍长期告警；滑动窗口让速率随闲置自然回落。
- **整数百分比必须挂置信度。** 22 分钟涨 2%，真实值可能是 1.4%，也可能是 2.5%，速率相差近两倍。第一版未分级，报出过「18 小时后耗尽」的错误警报。
- **无状态幂等。** 每次全量重算，不写缓存、不落状态文件。删除重跑、换机器、换目录结果一致。

## 已知局限

- 只有**服务端下发了 `quota` 快照**的模型才出现在报告中，而非「用过就有」。本机实测：`deepseek-v4.1-flash` 的记录全部带完整快照；`glm-5.3-flash` 只下发 `credit`（如 0.49 积分），`quota` 或为 `null`、或整键缺失。
- 不下发 `quota` 的模型（目前见到的 GLM 系列）只能看到积分消耗，无法计算增速与触限。
- 不发起对话则不刷新快照。
- 全量扫描，文件数增至上千后会变慢（需 mtime 缓存，见 TODO）。
- 单账号视图，多账号会混算。
- 时间按本机时区显示。
- 小窗依赖标准库 tkinter；未编入 tk 的解释器只能运行命令行版本（`--which` 可自查）。
- 小窗默认只列最严重的 3 个模型（`--max-rows` 可调），其余在页脚计数。
- `build_report` 中 `elif conf == "idle"` 一段位于 `conf in ("low", "none")` 分支内部，实际不可达，因此「近期没有新增消耗」的模型会落到 `ok / 按当前节奏够用`。此处只作记录，未改动判定链。
- **看不到账号级额度包余额**。该数据在账单接口 `v2/billing/meter/get-user-resource`，需要登录 token，而本机凭据由应用以 `$wbEncrypted` 加密。

## 附录：GLM 的额度存放位置

结论：**本地没有任何位置存放 GLM 的额度**。不是藏得深，是客户端从未收到。以下是逐处排查结果。

| # | 位置 | 查了什么 | 结果 |
|---|---|---|---|
| 1 | `projects/*/*.jsonl` | 187 条 GLM 记录的 `rawUsage` | `quota` 全为 `null` 或整键缺失；`credit` 正常（0.15 ~ 1.55） |
| 2 | `workbuddy.db` → `session_usage` | 全部表结构与行 | 只有 `credit_json`（按 request id 记录积分），无上限与余额 |
| 3 | `workbuddy.db` → `buddy_snapshots` | 表名近似「快照」 | 0 行，且列为应用模板快照，与额度无关 |
| 4 | `models.json` | 模型清单 | 空数组（2 字节） |
| 5 | `cache/acc-product-config-v3-*.json` | 60 个模型的配置 | 只有 `credits` 倍率（如 GLM-5.3-Flash `x0.08`）、上下文窗口、reasoning 档位，无按模型额度 |
| 6 | `local_storage/*.info`（含 4 个 base64 + gzip 大块） | 解压后 36 ~ 56 万字符 | 全为产品目录与功能开关；`ModelRateLimitCap` 只涉及 hy3/hy4 的免费与付费切换 |
| 7 | `plugin-account-state/*.json` | 账号状态 | 只有插件启停状态 |
| 8 | `app.asar`（174MB 前端本体） | 搜索 `shared_models` / `reset_at` | 0 命中，客户端不解析这两个字段 |
| 9 | `app.asar` 中处理 `rawUsage` 的代码 | 逐字节查看上下文 | 只读 `rawUsage.credit` 累加积分，`quota` 原样透传进 jsonl，不参与任何 UI |
| 10 | `app.asar` 中文文案 | `配额` / `积分` / `额度` | `配额` 0 命中，`积分` 0 命中，`额度` 仅出现在飞书连接器文档中 |
| 11 | `app.asar` 接口常量 | 额度相关路径 | 有 `/v2/billing/meter/checkin-activity-status`、`/v2/user/cloudagent/quota`、`/v2/billing/meter/get-enterprise-user-usage`，无按模型查询百分比的接口 |
| 12 | `logs/workbuddyMainThread*.log` | 上述接口是否被调用 | 只调用签到（`checkin-activity-status` 260 次），且日志只记录 `path` 与 token 长度，不记响应体 |

三条证据：

1. **客户端不解析**：`app.asar` 中搜索不到 `shared_models`、`reset_at`，说明前端从未计划展示模型配额，只在收到 `rawUsage` 时取 `.credit` 累加积分。
2. **客户端不查询**：没有「按模型查额度」的接口，只有签到、企业用量与云 agent 配额；签到调用也不回传模型百分比。
3. **服务端不下发**：187 次请求中，GLM 的 `quota` 一次都未出现；同窗口的 deepseek 为 187/187 全部下发。

因此查看 GLM 额度只有两条路，均在本工具之外：

- **网页账号页**（`https://www.workbuddy.cn/profile/plan`，配置中 `creditPurchaseActions` 指向它），积分余额与套餐在该页。
- **自行累加积分**：`rawUsage.credit` 存在，本工具已在报告中汇总（`credit_total`），但它无法换算成「还能支撑多久」。

要转为可监控的数字，理论上需调用 Billing 接口获取积分余额，需要登录态 token，而本机凭据是 `$wbEncrypted` 加密信封，本项目明确不涉及。这也是「GLM 的额度」在本版本中只显示积分消耗的原因。
