# 设计档案

> 实现细节、设计取舍、踩过的坑。快速上手看仓库根目录的 [README](../README.zh.md)。

读本机 WorkBuddy 会话日志里**服务端随响应下发的配额快照**，按模型算出「会不会在配额重置前耗尽」，
用于在额度被打满之前提前换模型或收尾，而不是事后统计已经花了多少。

纯标准库，Python 3.8+，只读本地文件，不联网、不登录、不上传。

---

## 为什么自己写

2026-11 对 GitHub 上 WorkBuddy 生态的调研结论：同类工具（token-watcher / token-ledger /
token-monitor / ai-quota-dashboard / wb-credits 等）绝大多数只做 token 与积分的**事后统计**，
没有一个读取模型级配额百分比。反面证据：

- `keros68/metrik` 的 WorkBuddy adapter 直接返回 `quotas: vec![]`
- `webkong/TokenViewer` 源码注释记录：曾读账号配额快照，后主动删除
- `luwill/token-watcher` 的官方配额栏只列 Claude / Codex / Cursor，WorkBuddy 不在内
- `ww330115/token-ledger` 的 quota 表是 opencode Go，WorkBuddy 侧只有积分

原因很朴素：配额百分比不在任何独立文件里，只藏在每轮请求日志中，扫 token 字段的人顺手就跳过了。

## 数据来源

```
%USERPROFILE%\.workbuddy\projects\<project-key>\<session-id>.jsonl
```

（国际版为 `~/.workbuddy-ai/projects/...`；可用环境变量 `WORKBUDDY_HOME` 覆盖根目录。）

关键记录形如：

```json
{
  "type": "function_call",
  "timestamp": 1793898134014,
  "providerData": {
    "model": "deepseek-v4.1-flash",
    "rawUsage": {
      "prompt_tokens": 32735,
      "completion_tokens": 196,
      "total_tokens": 32931,
      "credit": 0.11,
      "quota": {
        "model": "deepseek-v4.1-flash",
        "percent": 2,
        "reset_at": "1793975887",
        "shared_models": []
      }
    }
  }
}
```

| 字段 | 含义 | 备注 |
|---|---|---|
| `quota.percent` | 该模型配额已用百分比 | **整数**，这是精度硬伤，见下文 |
| `quota.reset_at` | 配额重置时间戳 | 秒级；本机为 24h 窗口，每天 22:38 重置 |
| `quota.shared_models` | 共用同一配额的模型 | 非空时消耗会互相影响 |
| `rawUsage.credit` | 本次请求消耗积分 | 用于累计，不参与判定 |
| `rawUsage.total_tokens` | 本次请求 token 数 | 同上 |

注意：`percent` / `reset_at` **随响应下发**，不聊就不刷新，所以报告里的时间是「最后一次响应」的时间。

## 哪些模型能看见限额（在本机逐条清点过）

以 `providerData.model` 为键、按「这一条记录里到底有没有 `quota` 字典」统计（早期按 `'"quota"' in line` 预筛会把
分母缩小，看到「几乎全都有」的假象，别再用那个口径）：

| 模型 | 记录数 | 带 quota | 情况 |
|---|---:|---:|---|
| `deepseek-v4.1-flash` | 3318 | 491（15%） | 唯一有百分比的模型，但只在 11-06 01:02 之后的会话里出现 |
| `deepseek-v4-pro` | 424 | 0 | 全部发生在 10-28~10-29，那时字段还没下发 |
| `glm-5.3-flash` | 187 | 0 | 10-27 ~ 11-06 02:14 全部无（早期整键缺失，11-06 起为 `null`） |
| `hy4-free` | 180 | 0 | 免费模型，`credit` 恒为 0，走的是限流而非配额 |
| `hy3` | 33 | 0 | 同上 |

两个维度叠加才解释得通：

- **时间维度**：`quota` 字段是 11-06 01:02 之后才开始随响应下发的。之前 45 个会话（含 deepseek 的 867/671/430 条）
  一条都没有 —— 所以「老日志里查不到限额」不是工具漏读，是当时服务端没给。
- **模型维度**：同一时间窗内（11-06 01:02 之后）deepseek 是 100% 带，GLM 是 0% 带。
  同版本、同会话、同并发，唯一变量就是模型，因此可以判定 GLM 不在「24h 模型配额」这套机制里。

**看不见限额的场景，以及原因**：

| 场景 | 现象 | 原因 |
|---|---|---|
| GLM 系列 | 永远无百分比 | 按积分倍率计费（`credits: x0.08`），服务端不下发 quota |
| `hy3` / `hy4-free` 免费模型 | 无百分比、无积分 | 走 `ModelRateLimitCap` 限流，可切付费版（`hy4free`→`hy4std`） |
| 11-06 之前的任何模型 | 无百分比 | 字段尚未开始下发 |
| 新装/未跑过的模型 | 列表里不出现 | 只有用过才有记录 |
| 长时间不聊 | 数字停住 | 快照随响应下发，不请求就不刷新 |
| 账号级额度包余额 | 完全不可见 | 需登录态查 Billing 接口，本机凭据是 `$wbEncrypted`，本项目不碰 |

一句话总结：**这套 24h 配额只覆盖 deepseek 一类模型；GLM 的「额度」是积分，而积分余额本地没有落点。**

## 用法

```bash
python quota_watch.py                 # 表格报告
python quota_watch.py --json          # 机器可读，接自动化/其他程序
python quota_watch.py --window 120    # 用最近 120 分钟算增速（默认 60）
python quota_watch.py --warn 6        # 预计 6 小时内触限就告警（默认 3）
python quota_watch.py --warn-only     # 无风险时静默，适合定时任务
```

退出码：`0` 无风险 / `1` 存在 `critical`。`--warn-only` + 退出码组合可让计划任务只在真出问题时通知。

Windows 下可直接双击 `run.bat`（内部等价于 `python quota_watch.py`，结束前暂停以便看清结果）。

## 常驻小窗（quota_tray.py）

右下角一块无边框卡片，把上面那张表压成「模型 / 百分比 / 一句判决」。
数字全部来自 `build_report()`，展示层不重算、不改写任何判定。

**平时它是一枚小胶囊**，写着「最近一次对话用的模型 + 它的占用」。鼠标碰上去停 180ms 就展开，
移开 2.2 秒收回。启动时直接是胶囊，不先摊开一次。

展开是「原地长出来」：**右下角钉死不移动**，底边不动、向上向左长，所以和胶囊连在一起，不会跳。
不压输入框靠的是**横向躲进输入框右侧的空档**（详见下方「摆放逻辑」）—— 卡片底边和胶囊齐平，
宽度收窄到刚好不越界；本机实测卡片左边 2164、输入框右边 2148，留 16px。

| 形态 | 尺寸（逻辑像素） | 内容 |
|---|---|---|
| 胶囊（默认闲置态） | 150 × 32 | 状态灯 + 最近用的模型 + 百分比 |
| 卡片（悬停展开） | 250 × 110 起（随空档自适应，上限 306） | 模型 / 进度条 / 判决 / 重置时间 |
| 完整报告（独立窗口） | 罩住对话内容区：宽 ≈ 输入框跨度，底边停在输入框上沿之上 | 每个模型的增速、ETA、样本、tokens、积分 |

```
┌───────────────────────────────┐
│ ● 配额胶囊           02:40  × │
├───────────────────────────────┤
│ deepseek-v4.1-flash      55%  │
│ ▬▬▬▬▬▬▬▬▬─────────────────────  │
│ 重置前耗尽 · 约 1.1 小时后     │
├───────────────────────────────┤
│ 重置 22:38 · 587 条快照  共 1 个│
└───────────────────────────────┘
```

### 什么时候出现

跟随 WorkBuddy 的**可见主窗口**，而不是只跟随进程：

| WorkBuddy 状态 | 小窗 |
|---|---|
| 打开且在前台 | 出现 |
| 切到别的应用（微信、浏览器…） | 约 3 秒后让路，切回来立刻出现 |
| 关掉主窗口 / 退到系统托盘 / 最小化 | 约 1.5 秒后隐藏 |
| 从托盘重新打开 | 重新出现 |
| 真正退出（进程消失） | 约 10 秒后自身退出 |

为什么三样都要看：

- **只盯进程** → 关窗后小窗赖着不走（WorkBuddy 支持关闭到托盘）。
- **只盯窗口（可见 + 有标题）** → WorkBuddy 进程里常驻着 `MSCTFIME UI`、`HintWnd`、
  `Sogou_TSF_UI` 这类 **0×0 的输入法辅助窗口**，它们 `IsWindowVisible=True` 且有标题，
  会被当成「主窗口」，于是主窗口关掉后状态仍然是 open —— 小窗永不隐藏，还会以置顶身份
  浮在微信上面。现在要求：真实尺寸（≥200×150）、无 owner、非工具窗口、非最小化、
  未被 DWM 隐藏（cloaked）。
- **不看前台** → 你在微信里打字，置顶的胶囊还压在上面。现在前台是别的应用超过 3 秒就
  让路；点小窗自己不会触发（会把自身进程排除掉）。不想要这个行为：右键
  「切到其他应用时隐藏」取消勾选。

上表的秒数是 `Lifecycle` 的判定阈值，不等于真实反应时间。真正落地要叠三段：探测线程
最多 1.5 秒才看到状态变化、UI 心跳最多再晚 1.5 秒记录时间戳、然后才是阈值本身。
所以「1.5 秒」这一档实测落在 **1.5~4.5 秒**，典型约 3 秒；「3 秒」那一档落在 3~6 秒。

冷启动（例如登录自启）时如果 5 分钟内一直没见到 WorkBuddy，它会自己退出，不留孤儿进程；
`--grace 0` 改成一直等着。

**两种收尾方式**，区别只在 WorkBuddy 真退出之后：

| 模式 | 行为 | 适合 |
|---|---|---|
| 默认（跟随） | 应用退出 → 小窗 10 秒后结束进程 | 自启由看门狗负责，小窗本身不常驻 |
| `--resident` | 应用退出 → 只隐藏，进程留着等它再开 | 想要「随时点开都秒出」且不在乎一个 90MB 进程 |

`--install` 现在装的是**看门狗 + 跟随模式**：登录时只起一个 ~27MB 的 WSH 脚本
（`tools/watchdog.tpl` 生成），它每 5 秒看一眼 `WorkBuddy.exe` 在不在，在就拉起小窗；
WorkBuddy 一退出，小窗按跟随模式自己结束。所以小窗是真正「随 WorkBuddy 起停」的，
登录后不再有一个 python 常驻。

手动点 × 关掉小窗会写一个 `suppress` 标记，看门狗 15 分钟内不会把它拉回来
（否则点一下五秒后又自己冒出来）；期间想再用，双击 `tray.bat` 即可。

### 启动与自启

```bash
python quota_tray.py              # 本次常驻
python quota_tray.py --install    # 写入登录启动项：开机静默待命，WorkBuddy 一开就出现
python quota_tray.py --uninstall  # 移除
python quota_tray.py --always     # 不看 WorkBuddy，强制显示（预览/截图用）
```

Windows 下双击 `tray.bat` 也行：它会自己挑一个带 tkinter 的解释器，控制台窗口随即消失。

**关于 tkinter**：小窗用标准库 tkinter 画，不引入任何第三方包。若当前 `python` 未编入 tk，
`--which` 会列出本机所有解释器及各自的 tk 状态；`tray.bat` 与 `--install` 会自动挑带 tk 的那个
（优先 pythonw，避免弹控制台）。本机实测：`.workbuddy/binaries/python` 下的三个解释器都没有
tkinter，系统装的 Python 3.14 有。

### 交互

| 操作 | 效果 |
|---|---|
| 拖动 | 横向纵向都能拖（胶囊态也能拖）；拖动只改本次会话的位置，**不写盘**，要右键「保存当前布局」才固化为启动位置 |
| 悬停 | 停留 180ms 自动展开（快速划过不触发）；卡片内整行浮起淡底 |
| 单击胶囊 | 立即展开（不等那 180ms） |
| 移开 | 2.2 秒后自动收回胶囊（鼠标还在卡片上会续期，拖动中或锁定时不收） |
| 单击某一行 / 「详情」 | 打开完整报告窗口（GUI，不再弹控制台）；窄卡（column 模式）放不下「详情」按钮时会隐藏它，右键菜单里仍有「完整报告」 |
| 右键 | 刷新 / 完整报告 / 在控制台打开 / 复制摘要 / **保存当前布局** / **恢复默认位置** / 重新校准位置 / 切到其他应用时隐藏 / 保持展开 / 置顶 / 开机自启 / **重启小窗** / 退出 |
| × | 退出 |

报告窗口的标题栏按钮（⟳ / ×）有悬停圆底反馈；小窗「详情」是一枚常驻细边框的圆角按钮。
大窗**整个窗口都能拖**（标题栏空白处光标变四向箭头 `fleur`，内容区也能按住拖 —— 画布上没有
可点选的元素，不会抢滚动），右键菜单也能保存/复位位置，不用非得去找标题栏那枚 chip。

默认落点是「距工作区右边 8、下边 35（Tk 单位，150% 缩放下即物理 12 / 52）」，正好让开任务栏上方的
输入法悬浮栏（搜狗那条常年贴在右下角）。

想换成自己的习惯位置：拖到满意处 → 右键「保存当前布局」→ 下次启动就停在那里。**拖动本身不写盘**：
拖了没保存，重启会回到上次保存的位置，误拖一下不会把布局改坏。想回到出厂落点就点「恢复默认位置」，
它会清掉存档并复位。

布局存在 `%LOCALAPPDATA%\quota-watch\tray.json` 的 `layout` 子树里（`tray` / `report` 两段，
都是「距工作区右下角的偏移」）：

```json
{"layout": {"tray": {"dx": 24, "dy": 51}, "report": {"dx": 261, "dy": 493}, "saved_at": "11-07 01:20"}}
```

存偏移而不是绝对坐标，换分辨率或缩放后「贴着右下角再挪一点」的意图不会漂。老版本只有平铺的
`dx/dy`、`report_dx/report_dy`，读取时仍然兼容；点过保存后只把**本次写入的那一段**迁进
`layout` 并清掉它的旧键 —— 另一段的旧键必须留着，否则保存小窗会把大窗位置一起清掉
（踩过这个坑：大窗位置被无声重置成默认落点，看起来像「位置锁死改不了」）。

小窗的偏移存的是**右下角**（锚点），窗口变宽时向左生长，右缘不会动 —— 所以收起成胶囊、
展开成卡片，两者右下角完全重合。

### 摆放逻辑（为什么不会压住输入框）

关键事实：WorkBuddy 的输入框是**一块有限宽的圆角卡片**（本机测量 `x 832~2148, y 1278~1477`），
不是一条通栏底边；它右边到屏幕右缘还留着 400px 宽的空档。所以「不遮挡」的正解是**横向**躲，
不是纵向抬走 —— 之前几版都按「底部整条都是输入区」去算，才会怎么调都压住。

`_plan()` 一次性算出「卡片多宽 / 放几行 / 底边在哪」，按优先级分三档：

| 模式 | 触发条件 | 行为 |
|---|---|---|
| `gutter` | 量到输入框右边缘，且右侧空档 ≥ 196 | 卡片宽度收进空档（本机 376px），**底边不动**，向上长 —— 真正的原地展开 |
| `column` | 量不到边缘 / 空档不够 | 宽度沿用胶囊那一列（已证明不压输入框），**只涨高不涨宽** |
| `free` | 关掉右键「展开时不压输入框」 | 恢复自由浮动，306 宽，可能压住 |

边缘怎么量：在胶囊中线高度附近取**三条**横线（`grab_strip`，各约 1~3ms），逐列统计
「与背景色显著不同」出现在几行里，从右往左找第一条**在多行上重复出现**的竖线 —— 那就是
输入框的右边框。判据是「竖线」，不依赖主题明暗：早期版本要求「边框左侧是实心块」，
浅色主题下输入框是白底白字加一条细灰边，这条恒不成立，校准永远量不到（issue #1）。

扫描带的右端停在**自己窗口左缘之前**（`origin[0] - px(4)`）。窗口是盖在宿主界面上的，
采样点一旦落进自己的窗口，背景色和特征列都会变成自己的像素 —— 早期版本就这样把自己
的边角量成了输入框边框，卡片越校准越窄（实测偏差 135~148px）。

量到就写进 `tray.json` 的 `input_edge`，之后一直复用；息屏 / 全黑 / 被别的窗口盖住时读不到，
就走 `column` 兜底。

右缘还有一条独立规则：`_place()` 一律让窗口右缘距屏幕右缘至少 16 逻辑 px（`RIGHT_RESERVE`），
给宿主窗口贴边的滚动条留位置 —— 胶囊压在滚动条上会一直若隐若现地硌眼。

底边的默认落点是 `BOTTOM_PIN=34` 逻辑 px —— 输入框底边距工作区底部正好 34（本机实测
1477/1528），所以刚装好时胶囊、展开卡片和输入框底边平齐，看着像「贴着输入框右缘长出来的一块」。
但这条线**不再强制钉死**：小窗可以自由拖到任意高度，位置按右下角偏移记住。

换过窗口大小、缩放或换过显示器后，右键「重新校准位置」重量一次即可。校准会把窗口先收成
胶囊再读屏 —— 展开的卡片正压在扫描线上，否则量到的是自己的左缘，卡片会随即往左长、盖住
输入框（这个坑踩过）。量完还会自检一次：按新边界算出的卡片左缘必须落在边界右侧，否则
宁可不采用。

几个刻意的取舍：

- **三级灰阶**：模型名（正文色）> 判决语（次级灰）> 页脚（再淡 30%）。眼睛先看模型和百分比，
  需要解释时才往下读，最后才是「重置时间 / 快照数」这种元信息。
- **行间发丝线**：行高 56 后三段文字（名称/进度/判决）各自有了呼吸空间，行与行之间再压一条
  极淡的分隔线，判决语不会再和下一行的模型名黏成一片。
- **百分比用等宽字体**（Cascadia Mono → Consolas），字号比模型名大一号、右对齐；数字等宽，
  从 9% 跳到 10% 时不会左右抖。
- **进度条 5px 高**，圆角收在两端，填充上还压一道 26% 的白色高光——Tk 没有 alpha，
  这条高光是用混色算出来的，让色块看起来有体积。
- **阴影三层**（由外到内递深），替代真实模糊阴影；卡片圆角 13。
- **颜色只表达判定**：红 / 橙 / 绿 / 灰对应 `critical` / `warn` / `ok` / `idle`，
  不做装饰性上色，避免和「危险」抢注意力。
- **空态/错误态是一枚小表盘**：用 `create_arc` 画的一段 220° 圆弧 + 指针，配居中的两行说明；
  卡片太矮（column 窄卡）时自动退化为纯文字居中，不放表盘。
- **胶囊灯 = 全场最危险**：收起态的状态灯颜色取所有模型里最严重的档位（`worst_level`），
  而不是最近对话模型的档位 —— 本工具的职责是「告诉你哪个先撞墙」，最近用的模型哪怕闲着，
  只要有模型快到上限，收起态也要亮红。胶囊文字仍显示最近对话的模型 + 它自己的百分比，
  数字颜色跟它自己的档位走（0% 就是灰的），灯和数字各说各的事。
- **深浅色跟随系统**：每 30 秒读一次注册表 `AppsUseLightTheme`，用户在系统里切主题，
  小窗自己跟着换，不用重启。
- **按像素省略**：模型名用字体实测宽度做二分截断，长名字能多露两三个字；
  卡片宽度在窄屏上会自动收，不会顶到屏幕边。
- **收起/展开钉住右下角**：形态切换按右下角锚点重算，右边缘、底边都不动，向上向左生长；
  配合 130ms 缓出动画，看起来是「长出来」而不是「跳过去」。
- **完整报告是真正的窗口**：位置和尺寸按对话内容区定（2026-11-06 用户圈定）——
  宽 870 逻辑 px ≈ 输入框横向跨度，右缘与输入框右缘平齐（`input_edge` 量不到才水平居中），
  顶部距工作区顶 20 逻辑 px，底边让开输入框上沿右侧的吉祥物（INPUT_GAP=162 逻辑 px）——
  正好罩住对话区、不盖标题栏、不压输入框也不挡吉祥物。**拖动后可保存**：拖完标题栏标题右侧
  会浮出一枚「保存位置」chip，点它才把当前位置固化为启动位置；不点就关掉，下次打开还是上次
  保存的地方（误拖不会改坏布局）。存档与小窗共用 `layout` 子树，`report` 段。
  **标题带与卡片同色 + 底部分隔线**，
  整窗融进 WorkBuddy 的白色系，读起来像应用自己的一块面板（深色主题同理与卡片同色）；
  自绘标题栏（可拖动）、⟳ 刷新、× 关闭、
  Esc 关闭，两个按钮悬停时会点亮圆底；内容列限宽居中（最大 700 逻辑 px，宽屏上进度条不再横跨
  全窗），卡片 → 图例（一行四档色标，口径说明文字已删）→ 页脚建议排成一个内容栈：
  放得下就整体垂直居中，放不下（模型多）
  整栈滚轮滚动，标题栏固定不滚，右缘有细滚动指示条 —— 旧版卡片按绝对坐标画，7 个模型时
  漫过图例区叠印成一团，已修。
  每张模型卡是**白卡 + 细边 + 一层浅影 + 左侧档位色条**：名称/百分比 → 进度条（带高光）→ 判决语，
  分隔线以下是两行「标签 + 值」的档案行（重置/增速/距重置、触限预测/样本/置信，标签压淡、
  数值站出来），末行是 tokens 与积分。底部建议放进一枚语义色淡底的提示框：有风险时红调浮出，
  没有风险时安静灰底。控制台版本没删，右键「在控制台打开」还能用。

内部几处开销说明：全量扫日志是几百毫秒量级（本机 58 个会话文件 / 76MB / 1348 条快照，
实测 660ms；日志继续长就继续变慢），放后台线程；报告窗的
⟳ 刷新也是后台读，标题栏不会冻住。进程+窗口探测常态 **约 4ms**（窗口枚举 2ms + 校验缓存 pid
1.3ms）；10ms 量级的进程全量枚举（300+ 进程）只在缓存失效或每 20 秒兜底重扫时发生 ——
因为 WorkBuddy 的 pid 在会话内几乎不变，常态只需 `OpenProcess` + 核对 exe 名（约 0.05ms/个）。
探测放后台线程、1.5 秒一次（`--poll`），对应 CPU 约 0.25% 单核。隐藏阈值只有 1.5 秒，
探测周期必须跟得上，所以不再像早期那样在隐藏态降到 5 秒 —— 那会把 1.5 秒的阈值拉成
四五秒。只有 `--resident`（应用退出后长期待命）才在 gone 状态用 5 秒省 CPU（`--poll-idle`）。

## 处理逻辑

**1. 采集**：全量扫 `projects/*/*.jsonl`，先做 `'"quota"' in line` 字符串预筛，命中才 `json.loads`。
48 个文件 / 45 条快照约 0.2 秒。

**2. 增速**：以最新快照为锚点，取 `--window` 内首尾两条，`rate = Δ百分比 ÷ Δ小时`。
窗口内不足两条时，退化为「所有低于最新值的记录 + 最新一条」，再不足退回最后两条。

**3. 置信度**：`percent` 是整数，短样本会放大速率，因此分档：

| 档位 | 条件 |
|---|---|
| high | 跨度 ≥ 120 分钟且涨幅 ≥ 3% |
| medium | 跨度 ≥ 30 分钟且涨幅 ≥ 1% |
| low | 其余（含数据不足） |

**3.5 周期口径**（`PERIOD_H = 24`）：

配额池按 24 小时一轮回。`reset_at` 是**下一次**重置时刻，所以本周期起点 =
`reset_at - 24h`。两件事都按这个边界算：

- **过期快照**：若 `now > reset_at`（+60 秒宽限），说明这条快照属于上一周期，
  模型在**本周期还没被用过**。它会被标成 `stale`，不显示、不参与风险判定 ——
  否则就会出现「重置后一次没用，却还显示 11%，距重置 已过期」这种自相矛盾的读数。
- **tokens / 积分**：只累加本周期内的快照（`tokens_cycle` / `credit_cycle`），
  与屏幕上那个百分比属于同一段账。历史累计仍保留在 `tokens_total` / `credit_total`。

**4. 判定**（顺序执行，命中即返回）：

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 已用 ≥ 95% | `critical` 已到上限 |
| 2 | 置信度低且已用 ≥ 80% | `critical` 按最坏打算 |
| 3 | 置信度低（其余情况） | `idle` 只报现状，不预测 |
| 4 | 预计触限 **早于** 重置时间 | `critical` 重置前会耗尽 |
| 5 | 预计触限 < `--warn` 小时 | `warn` |
| 6 | 其余 | `ok` |

## 设计取舍

- **不比绝对值，只比重置时间。** 剩 50% 但一小时烧 30% 才危险；剩 20% 却还有 20 小时才重置其实安全。百分比本身没有决策意义。
- **用滑动窗口而非累计均值。** 累计会把上周的重度使用带进来，导致休息时也长期告警；滑动窗口让速率随闲置自然回落。
- **整数百分比必须挂置信度。** 22 分钟涨 2% 可能真实是 1.4%，也可能 2.5%，速率能差近两倍。第一版没做分级，直接报了个「18 小时后耗尽」的假警报。
- **无状态幂等。** 每次全量重算，不写缓存、不落状态文件；删了重跑、换机器、换目录结果一致，不会留下脏数据。

## 已知局限

- 只有**服务端下发了 `quota` 快照**的模型才会出现在报告里，而不是「用过就有」。本机实测：
  `deepseek-v4.1-flash` 461/461 条记录都带完整快照；`glm-5.3-flash` 只下发 `credit`（如 0.49 积分），
  `quota` 要么是 `null`、要么整个键都不存在 —— 这类请求会被跳过不是漏读，是数据里本来就没有百分比
- 不下发 `quota` 的模型（目前见到的 GLM 系列）只能看到积分消耗，无法算增速、也无法预测触限
- 不聊就不刷新配额快照
- 全量扫描，文件涨到上千个后会变慢（需加 mtime 缓存，见 TODO）
- 单账号视图，多账号会混算
- 时间按本机时区显示
- 小窗依赖标准库 tkinter；没编入 tk 的解释器只能跑命令行（`--which` 可自查）
- 小窗默认只列最严重的 3 个模型（`--max-rows` 可调），其余在页脚计数
- `build_report` 里 `elif conf == "idle"` 那段写在 `conf in ("low", "none")` 分支内部、实际不可达，
  所以「近期没有新增消耗」的模型落到 `ok / 按当前节奏够用`。此处只记录，未改动判定链
- **看不到账号级额度包余额**（那是账单接口 `v2/billing/meter/get-user-resource` 的数据，需登录 token；本机凭据被应用以 `$wbEncrypted` 加密）

## 附录：GLM 的限额到底存在哪（本地排查全过程）

结论先说：**本地没有任何地方存放 GLM 的额度**。不是藏得深，是客户端根本没收到过。下面是把本机翻遍的路径，
以及每一处「有没有、是什么」。

| # | 位置 | 查了什么 | 结果 |
|---|---|---|---|
| 1 | `projects/*/*.jsonl` | 187 条 GLM 记录的 `rawUsage` | `quota` 全为 `null` 或整键缺失；`credit` 正常（0.15~1.55） |
| 2 | `workbuddy.db` → `session_usage` | 全部表结构 + 行 | 只有 `credit_json`（按 request id 记积分），无上限/余额 |
| 3 | `workbuddy.db` → `buddy_snapshots` | 表名像「快照」 | 0 行，且列是应用模板快照，与额度无关 |
| 4 | `models.json` | 模型清单 | 空数组（2 字节） |
| 5 | `cache/acc-product-config-v3-*.json` | 60 个模型的配置 | 只有 `credits` 倍率（如 GLM-5.3-Flash `x0.08`）、上下文窗口、reasoning 档位；**无 per-model 额度** |
| 6 | `local_storage/*.info`（含 4 个 base64+gzip 大块） | 解压后 36~56 万字符 | 全是产品目录/功能开关；`ModelRateLimitCap` 只对 hy3/hy4 的免费↔付费切换，与 GLM 无关 |
| 7 | `plugin-account-state/*.json` | 账号状态 | 只有插件启停状态 |
| 8 | `app.asar`（174 MB 前端本体） | 搜 `shared_models` / `reset_at` | **0 命中**——客户端不解析这两个字段 |
| 9 | `app.asar` 里处理 `rawUsage` 的代码 | 逐字节看上下文 | 只读 `rawUsage.credit` 累加积分，`quota` 被原样透传进 jsonl，不参与任何 UI |
| 10 | `app.asar` 中文文案 | `配额` / `积分` / `额度` | `配额` 0 命中，`积分` 0 命中，`额度` 仅出现在飞书连接器文档里 |
| 11 | `app.asar` 接口常量 | 额度相关路径 | 有 `/v2/billing/meter/checkin-activity-status`、`/v2/user/cloudagent/quota`、`/v2/billing/meter/get-enterprise-user-usage`；**没有**按模型查百分比的接口 |
| 12 | `logs/workbuddyMainThread*.log` | 上面那些接口是否真被调用 | 只调了签到（`checkin-activity-status` 260 次），且日志只记 `path` 和 `token` 长度，不记响应体 |

三条硬证据：

1. **客户端不解析**：`app.asar` 里 `shared_models`、`reset_at` 一个字符都搜不到，说明前端从没打算展示模型配额；
   它只在收到 `rawUsage` 时取 `.credit` 做积分累加。
2. **客户端不查询**：没有「按模型查额度」的接口，只有签到/企业用量/云 agent 配额；签到调用也不回传模型百分比。
3. **服务端不给**：187 次请求，`quota` 一次都没出现在 GLM 的响应里，而同窗口的 deepseek 是 187/187 都给。

所以要看 GLM 的额度，只有两条路，都在本工具之外：

- **网页端账号页**（`https://www.workbuddy.cn/profile/plan`，配置里 `creditPurchaseActions` 指向它）——积分余额与套餐在那里；
- **自己累加积分**：`rawUsage.credit` 是有的，本工具已经在报告里汇总（`credit_total`），只是它不能换算成「还能撑几个小时」。

要把它变成可监控的数字，理论上得调 Billing 接口拿积分余额 —— 需要登录态 token，而本机凭据是
`$wbEncrypted` 加密信封，本项目明确不碰。这也是为什么「GLM 的额度」在这一版里注定只显示积分消耗。
